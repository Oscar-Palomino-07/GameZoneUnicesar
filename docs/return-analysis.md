# Return Analysis — GameZone Unicesar

> Answers to the five orienting questions of the return module (exam Requerimiento 3),
> written against the implemented code: `Return`, `ReturnRepository` and `ReturnService`.

## Q1: How is a return modeled, and why does it store the `saleId` instead of a whole `Sale` reference?

A return is modeled by the `Return` class in the model layer. It holds the identifier
generated by the service (`D-1`, `D-2`, ...), the date captured automatically in the
constructor, the customer and the seller who took part in the original transaction, and
the list of products that are being given back. The refund amount and the printed receipt
are derived from those products through `calculateRefundAmount()` and
`generateReturnReceipt()`.

Instead of a `Sale` reference, `Return` keeps a `saleId: String`. This is the same decision
already used by `Warranty`, which persists the sale and product identifiers rather than the
objects themselves. The reasons are: a return is a historical fact that must survive even if
the original sale is inspected or edited later, so the link must be explicit and stable; a
`String` identifier has no identity of its own, so it can never be confused with a second
copy of the same sale loaded from the file; and the file stays small and easy to read.
The original sale is still reachable when it is needed: `ReturnService` receives
`SaleService` and calls `findById(saleId)` to validate the return.

## Q2: Where is the rule "a sale can only be returned within 30 days" enforced, and which Java mechanism implements it?

The rule lives in the model as the concrete method `Sale.canBeReturned()`, which computes
`ChronoUnit.DAYS.between(date, today)` and accepts the sale while the result is between 0
and 30 inclusive. `ReturnService.registerReturn` is the place that enforces it: it locates
the original sale and rejects the operation with `IllegalArgumentException` when
`canBeReturned()` is false, so the rule is applied before any stock is restored.

The date rule belongs to the model because it is a property of the sale itself ("this sale
is still returnable"), it needs only the sale date and today's date, and it changes no
state. Keeping it in the model guarantees that every caller gets the same answer, whereas
duplicating the arithmetic in the service or in the menu would let the two drift apart.
The mechanism used is `java.time.temporal.ChronoUnit`, which expresses the difference in
days directly instead of the error-prone arithmetic with `millis()`.

## Q3: When a product is returned, which class restores its stock, and why is that not done in the repository?

`ReturnService.registerReturn` calls `ProductService.restoreStock(productId, quantity)` once
the return has been fully validated, and `ProductService` updates the in-memory product and
persists the new inventory immediately through `ProductRepository`.

Restoring the stock is a business operation, not a storage operation, so it belongs to the
service layer. The repository may only read and write files: if it decided how much stock to
add, the same rule would have to be duplicated for products and for accessories, and the
UI could bypass it. `ProductService` is also the only class that owns the product inventory
list, which is why it is the one that can add the units back and save them. Note the order
inside `registerReturn`: every validation (the sale exists, the period is open, the items
were part of the sale, no double return) runs first, so a rejected return never leaves the
inventory modified.

## Q4: How are partial returns and repeated returns of the same item detected?

`registerReturn` receives the identifiers of the items to return, repeated once per unit,
and builds a map of quantities with `Map.merge(id, 1, Integer::sum)`. For each identifier it
counts how many units of it the original sale contains, and it counts how many units were
already returned in previous returns of the same sale with
`countAlreadyReturnedByProduct`. Two different failures are then distinguished:

- More units requested than were purchased is an invalid request and raises
  `IllegalArgumentException`.
- The units were purchased but were already given back, so the data is inconsistent; this
  raises `IllegalStateException`.

Because the same `productIds` list can carry an identifier more than once, partial returns
work naturally: returning one of two identical consoles stores a `Return` with a single
product, and the next call sees `previouslyReturned = 1` against `qtyBought = 2` and
accepts the second one.

## Q5: Where is the monthly balance report computed, and which three values does it need?

The report is computed in the service layer, in `ReturnService`, because it combines data
that lives in two different registries: the sales, owned by `SaleService`, and the returns,
owned by the in-memory list of `ReturnService`. The method `generateMonthlyBalance(month,
year)` validates the month (1-12) and the year, adds `Sale.calculateTotal()` for every sale
whose date falls inside the requested month and year, adds
`Return.calculateRefundAmount()` for every return of that month, and returns the
difference. The model classes are not asked to do it because neither `Sale` nor `Return`
knows about the other, and the console menu is not asked to do it because the user
interface must not contain business rules.

Two safeguards protect the result. The comparison uses
`sale.getDate().getMonthValue()` and `getYear()`, so a sale from another month or another
year never enters the sum. And a negative balance raises `IllegalStateException` instead of
being printed, because refunds larger than the sales of a month mean the stored returns are
inconsistent and the user should be told instead of receiving a meaningless number.
